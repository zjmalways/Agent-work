# 接口文档（统一字段约定与协议说明）

## 1. 文档目的

本文档用于统一后端接口、前端字段、SSE 事件格式、任务状态与记忆结构，确保四个角色在并行开发时使用相同字段名和数据格式，避免因命名不一致导致联调失败。

统一原则：
- 所有接口返回统一采用 `code` / `message` / `data` 三段结构。
- 所有数据对象字段命名必须遵循保守、稳定、统一命名规则，禁止各模块自行扩展不同字段名。
- 前端和后端必须以本文档为唯一接口协议，不得私下约定字段。
- 若新增字段，必须先在这里更新并同步给所有角色。

---

## 2. 统一响应格式

所有 HTTP 接口返回格式如下：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

### 2.1 字段说明

- `code`: 响应码，`0` 表示成功，其他值表示失败。
- `message`: 简短描述，成功时通常为 `success`，失败时给出错误说明。
- `data`: 实际返回内容，允许为对象、数组、空对象等。

### 2.2 常用响应码

| code | 含义 | 说明 |
|---|---|---|
| 0 | success | 成功 |
| 400 | bad_request | 参数错误、格式错误 |
| 401 | unauthorized | 未授权 |
| 404 | not_found | 资源不存在 |
| 409 | conflict | 状态冲突，例如重复确认 |
| 422 | validation_error | 业务参数校验失败 |
| 429 | too_many_requests | 调用频率超限 |
| 500 | internal_error | 服务器内部错误 |
| 503 | service_unavailable | 工具服务不可用或超时 |

### 2.3 统一错误示例

```json
{
  "code": 422,
  "message": "时间不能早于当前时间",
  "data": {
    "field": "start_time",
    "error_type": "past_time_not_allowed"
  }
}
```

## 3. 通用数据对象

以下对象定义为全局标准，任何接口中出现这些字段时必须使用同名、同类型。严禁“startTime”与“start_time”混用。严格统一如下：

### 3.1 任务对象 Task

```json
{
  "task_id": "string",
  "user_id": "string",
  "user_input": "string",
  "status": "pending | running | waiting_confirmation | completed | failed | cancelled",
  "plan": ["string"],
  "current_step": 0,
  "step_count": 0,
  "result_summary": "string | null",
  "created_at": "ISO 8601 datetime",
  "updated_at": "ISO 8601 datetime",
  "started_at": "ISO 8601 datetime | null",
  "finished_at": "ISO 8601 datetime | null",
  "error_message": "string | null",
  "execution_time_ms": 0
}
```

字段说明：
- `task_id`: 全局唯一任务 ID。
- `user_input`: 用户原始输入。
- `plan`: 分阶段任务计划列表。
- `current_step`: 当前执行到的步骤序号，内部统一为 0-based；前端展示时按 1-based 转换。
- `status`: 统一状态枚举。
- `step_count`: 已生成或执行的步骤数量。
- `result_summary`: 最终结果摘要，适合前端展示最终结论。
- `created_at` / `updated_at`: 时间戳必须为 ISO 8601 格式，例如 `2026-10-12T18:00:00+08:00`。

### 3.2 步骤对象 Step

```json
{
  "step_id": "string",
  "task_id": "string",
  "index": 0,
  "description": "string",
  "status": "pending | running | success | failed | waiting_confirmation",
  "tool_name": "string | null",
  "tool_args": {},
  "tool_result": {},
  "error_message": "string | null",
  "started_at": "ISO 8601 datetime | null",
  "finished_at": "ISO 8601 datetime | null",
  "retry_count": 0,
  "waiting_for_confirmation": false
}
```

字段说明：
- `tool_name`: 当前步骤调用的工具名。
- `tool_args`: 工具调用参数。
- `tool_result`: 工具执行返回。
- `status` 与 `waiting_for_confirmation` 的关系：
  - 若某一步需要写操作确认，则 `status = waiting_confirmation`，且 `waiting_for_confirmation = true`。
  - 任务整体状态可能同时为 `waiting_confirmation`，但语义不能混淆。

### 3.3 任务确认对象 Confirmation

```json
{
  "confirmation_id": "string",
  "task_id": "string",
  "step_id": "string",
  "tool_name": "string",
  "payload": {},
  "status": "pending | confirmed | cancelled | expired",
  "created_at": "ISO 8601 datetime",
  "confirmed_at": "ISO 8601 datetime | null"
}
```

### 3.4 工具调用日志对象 ToolCallLog

```json
{
  "log_id": "string",
  "task_id": "string",
  "step_id": "string",
  "tool_name": "string",
  "request_payload": {},
  "response_payload": {},
  "success": true,
  "error_code": "string | null",
  "error_message": "string | null",
  "duration_ms": 0,
  "created_at": "ISO 8601 datetime"
}
```

### 3.5 记忆对象 MemoryItem

```json
{
  "memory_id": "string",
  "user_id": "string",
  "memory_type": "preference | task_history | system_note",
  "key": "string",
  "value": {},
  "created_at": "ISO 8601 datetime",
  "updated_at": "ISO 8601 datetime"
}
```

### 3.6 工具定义对象 ToolDefinition

```json
{
  "name": "string",
  "description": "string",
  "parameters": {
    "type": "object",
    "properties": {},
    "required": ["string"],
    "additionalProperties": false
  },
  "timeout_ms": 10000,
  "dangerous": false
}
```

## 4. 接口总览

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/agent/run` | 提交任务，异步执行，SSE 流式返回轨迹 |
| POST | `/api/agent/confirm` | 确认待定的写操作 |
| GET | `/api/agent/tasks` | 获取任务列表 |
| GET | `/api/agent/tasks/{task_id}` | 获取某个任务的完整轨迹 |
| GET | `/api/tools` | 获取工具注册清单 |
| GET | `/api/memory` | 获取当前用户长期记忆 |
| DELETE | `/api/memory` | 清除长期记忆 |

## 5. 接口详情

### 5.1 POST `/api/agent/run`

用于提交一个任务并开始执行。

#### 请求体

```json
{
  "user_input": "帮我查这周六下午有没有空，然后订活动室",
  "session_id": "sess_123",
  "user_id": "user_001"
}
```

字段说明：
- `user_input`: 必填，用户原始请求。
- `session_id`: 可选，当前会话 ID，用于短期记忆。
- `user_id`: 可选，当前用户 ID，用于长期记忆和权限控制。

#### 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "task_id": "task_abc123",
    "status": "running"
  }
}
```

#### 失败响应

```json
{
  "code": 400,
  "message": "user_input不能为空",
  "data": {}
}
```

#### 说明
- 本接口本身返回任务启动信息。
- 任务执行过程通过 SSE 继续推送，前端不要依赖此接口返回最终结果。
- 若输入内容包含注入尝试，应直接拒绝，不执行写操作。
- `stream_url` 可选，不要求强制返回；若用独立 SSE 地址，必须与后端实现一致，且统一在协议中说明。

---

### 5.2 POST `/api/agent/confirm`

用于确认待执行的写操作。

#### 请求体

```json
{
  "task_id": "task_abc123",
  "step_id": "step_003",
  "confirmation_id": "confirm_001",
  "confirmed": true
}
```

字段说明：
- `step_id`: 待确认步骤的唯一 ID。
- `confirmation_id`: 对应待确认记录的唯一 ID。
- `confirmed`: 是否确认执行。

#### 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "task_id": "task_abc123",
    "step_id": "step_003",
    "status": "running"
  }
}
```

#### 失败响应

```json
{
  "code": 409,
  "message": "当前确认已过期或已处理",
  "data": {}
}
```

#### 说明
- 此接口必须保证：
  - 未确认前不得真正落库
  - 已确认后才允许执行写操作
  - 重复确认必须被拒绝

获取当前用户的任务列表。

#### 正常响应

```json

  "message": "success",
  "data": {
    "items": [
      {
        "task_id": "task_abc123",
```

#### 说明
- 此接口返回任务概览，不返回详细步骤内容。

获取已注册工具清单，供前端展示和校验。

#### 正常响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "tools": [
      {
        "name": "room_availability_check",
```

### 5.7 DELETE `/api/memory`

清除长期记忆。

支持两种调用方式，必须在后端实现并统一前端使用：

#### 方式 A：删除单条记忆

```http
DELETE /api/memory/{memory_id}
```

#### 方式 B：清空全部记忆

```http
DELETE /api/memory?mode=all
```

#### 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "deleted_count": 1
  }
}
```

#### 说明
- 删除单条记忆时优先使用路径参数，不建议依赖 DELETE 请求 body。
- 清除全部记忆时统一使用 `?mode=all`。
- 前端必须展示清除成功/失败状态。

## 6. SSE 事件格式

任务执行过程中通过 SSE 推送事件流，前端用于展示“思考 → 选工具 → 调用 → 观察结果 → 下一步”的完整轨迹。

### 6.1 事件结构

```json
{
  "event": "task_step_update",
  "task_id": "task_abc123",
  "step_id": "step_001",
  "timestamp": "2026-10-12T18:00:00+08:00",
  "data": {
    "status": "running",
    "description": "开始检查会议室空闲时间",
    "tool_name": "room_availability_check",
    "tool_args": {
      "date": "2026-10-17",
      "time_start": "14:00",
      "time_end": "17:00"
    }
  }
}
```

### 6.2 推荐事件类型

| event | 含义 |
|---|---|
| `task_started` | 任务开始 |
| `task_status_update` | 任务状态更新 |
| `step_started` | 步骤开始 |
| `step_update` | 步骤状态变更 |
| `tool_call` | 工具调用事件 |
| `tool_result` | 工具执行返回 |
| `waiting_confirmation` | 等待确认 |
| `task_finished` | 任务完成 |
| `task_failed` | 任务失败 |
| `task_cancelled` | 任务取消 |

### 6.3 SSE 格式

服务端按 SSE 标准发送：

```text
event: task_step_update

data: {"event":"task_step_update","task_id":"task_abc123","step_id":"step_001","timestamp":"2026-10-12T18:00:00+08:00","data":{"status":"running"}}

```

说明：
- 每条事件以 `event:` + `data:` 形式发送。
- `data` 内部必须是 JSON 字符串。
- 前端必须按 `event` 类型分别处理，不允许把所有事件都当作同一种状态处理。

## 7. 状态统一标准

### 7.1 任务状态

| 状态 | 含义 |
|---|---|
| `pending` | 等待执行 |
| `running` | 执行中 |
| `waiting_confirmation` | 等待写操作确认 |
| `completed` | 已完成 |
| `failed` | 执行失败 |
| `cancelled` | 已取消 |

### 7.2 步骤状态

| 状态 | 含义 |
|---|---|
| `pending` | 等待执行 |
| `running` | 正在执行 |
| `success` | 执行成功 |
| `failed` | 执行失败 |
| `waiting_confirmation` | 等待确认 |

### 7.3 确认状态

| 状态 | 含义 |
|---|---|
| `pending` | 等待确认 |
| `confirmed` | 已确认 |
| `cancelled` | 已取消 |
| `expired` | 已过期 |

## 8. 字段命名规范（强制）

为避免各角色使用不同字段，以下命名必须统一：

- `task_id`，不能使用 `id` 或 `taskId`
- `step_id`，不能使用 `stepId`
- `user_input`，不能使用 `input` 或 `query`
- `created_at`，不能使用 `createTime` 或 `createdAt`
- `updated_at`，不能使用 `updateTime`
- `status`，统一枚举值
- `tool_name`，不能使用 `name` 代替（工具名字段需保留）
- `tool_args`，不能使用 `params`、`arguments`、`request`
- `tool_result`，不能使用 `result`、`response`
- `confirmation_id`，不能使用 `confirmId`

强制统一规则：
- 所有 JSON 字段使用 snake_case。
- 时间字段统一为 ISO 8601 字符串。
- 复杂对象统一使用 `data` 包裹。
- 不允许混用：
  - `task_id` / `taskId`
  - `created_at` / `createdAt` / `createTime`
  - `tool_args` / `params` / `arguments`
  - `tool_result` / `result` / `response`
  - `step_id` / `stepId`
  - `confirmation_id` / `confirmId`

## 9. 任务与步骤关系说明

为避免前端和后端理解不一致，必须明确以下关系：

- `plan`：规划器产出的步骤建议方案，属于任务蓝图。
- `steps`：任务实际执行过程中的步骤状态列表，属于执行信息。
- `current_step`：内部计数使用 0-based，表示当前执行到哪个步骤索引。
- 前端展示时，需将 `current_step + 1` 显示为“第 N 步”。
- 若 `status = waiting_confirmation`，则任务被挂起；但必须同时检查对应 `step.status` 是否为 `waiting_confirmation`。

---

## 10. SSE 事件语义规范

SSE 事件必须遵守以下统一规则：

- `event` 仅允许从标准事件表中选取，不允许前端自行定义新事件名。
- 每条事件都必须包含：`event`、`task_id`、`timestamp`、`data`。
- `data` 中必须使用统一字段命名，不能混用 `result` / `response` / `params` / `arguments`。
- `step_update` 事件必须带上 `step_id` 与 `status`。
- `waiting_confirmation` 事件必须同步包含确认相关信息：`step_id`、`confirmation_id`、`tool_name`。

示例：

```json
{
  "event": "step_update",
  "task_id": "task_abc123",
  "timestamp": "2026-10-12T18:00:00+08:00",
  "data": {
    "step_id": "step_001",
    "status": "waiting_confirmation",
    "tool_name": "create_schedule",
    "confirmation_id": "confirm_001"
  }
}
```

## 11. 接口开发约束（团队必须遵守）

1. 所有接口必须返回统一格式。
2. 所有字段命名必须使用 snake_case。
3. 所有时间必须使用 ISO 8601。
4. 所有工具调用必须记录原始 request 和 response。
5. 所有写操作必须有确认状态，不允许直接落库。
6. 所有失败必须明确返回错误码和说明。
7. 所有前端都只能依赖这里定义的字段，禁止自己发明字段。
8. 若新增字段，必须同步更新本文档并通知全员。
9. `DELETE /api/memory` 必须使用路径参数或 `?mode=all`，不建议依赖请求体。
